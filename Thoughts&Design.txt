I started with the simplest idea I could think of: just have the model compare field names and descriptions and find the best match. That broke almost immediately. Take something like emp_id. It is semantically close to _id in pretty much every collection, so the model would happily map it to employees, departments, or locations depending on the day. Field-level context alone was not cutting it.
So I added table context as a hard constraint. emp_id lives in emp_master, which means it should map to something in the employees collection, not wander off into departments or locations. Once I narrowed the search space like that, the candidate matches got a lot cleaner.
For the actual retrieval, I moved past pure semantic search and built a hybrid scoring system. Semantic embeddings are great at catching meaning. They understand that f_name and firstName are the same concept, but they can miss obvious keyword matches or exact abbreviations. I combined semantic similarity with a lightweight BM25 keyword score, weighting semantics at 70% and keyword overlap at 30%. In practice that blend worked well. It catches conceptual relationships but still respects exact naming conventions.
I also kept the LLM's job intentionally small. Instead of dumping both full schemas into one giant prompt and hoping for the best, I only feed the model a focused prompt with the source field, its table context, a shortlist of top candidate targets, their similarity scores and datatypes, plus a few hard mapping rules. The model picks the best candidate, writes a one-sentence reasoning, and flags any value transforms needed. Everything predictable, like datatype conversions, JSON formatting, and conflict resolution, I handle in regular code. That way the LLM does what it is actually good at, judgment and nuance, while code handles what it is good at, consistency and structure.
The full pipeline goes like this: normalize the schemas, enrich field semantics, run hybrid retrieval scoped to the relevant table, do batched LLM verification, then deterministic formatting and conflict resolution. No single prompt ever sees both complete schemas at once, which satisfies the core constraint and keeps token costs from ballooning.
